Question 1

Does adding more chips actually help?

In theory, using 4 chips instead of 1 should make a job 4 times faster. In practice, the chips have to spend a little time coordinating with each other, so you never get the full 4×. "Efficiency" here means how close the real result got to that perfect 4× (or 2×) number. Tested on the top-tier chip (H100), the primary hardware for this project.

Efficiency when you scale the job up with the hardware

Give each extra chip its own extra slice of work — the easier scaling case

Efficiency when you split one fixed job further

Keep the total job the same size and spread it across more chips — the harder case

Finding Adding chips paid off almost every time we tried it

When the job grows along with the hardware, both models we tested this way stayed at 91–97% efficient all the way up to 4 chips — essentially the full benefit. When we instead kept one fixed-size job and split it across more chips, efficiency fell off a bit faster (down to 73% for the text-classification model at 4 chips), which is expected: more chips means more back-and-forth coordination for the same amount of work.

Based on 48 completed test runs on the H100 chip across three model types.

Question 2

What's the best way to split work across several chips?

There are a few different ways to divide an AI model across multiple chips. Think of it like splitting a big printed report across several photocopiers: you can give every machine a full copy (fast, but each one needs the whole document in front of it), or you can split the document into sections and only hand each machine the pages it needs (slower to organise, but every machine needs far less desk space).

Finding The "memory-smart" method was the safest default

The full-copy method ("DDP") is the simplest and often fastest when memory isn't tight. But the memory-smart method ("FSDP") matched or beat it on speed while using noticeably less memory in almost every test we ran — for the text-classification model it was both 1.7% faster and used 10% less memory at the same time. The deepest memory-saving mode helped further only when memory was genuinely the bottleneck, and it cost real speed to get there.

Based on 35 matched H100 comparisons across two model types and multiple chip counts.

Question 3

Does it matter how precisely we store the numbers?

Every number inside an AI model can be stored with more or less precision — a bit like the difference between a large, exact photo file and a compressed one. The compressed version is much faster to move around and barely looks different, unless you compress it too far.

Text-classification model — training speed

Same comparison · speed multiplier vs. the most exact format

Finding Compressed number formats were the single biggest speed win we found

Moving from the most exact number format to a more compact one made training 2.6–3.6× faster for the text-generation model, and 4.7–5.3× faster for the text-classification model — on the exact same chip, doing the exact same job. And in a direct head-to-head accuracy check, the compact format got exactly the same number of answers right (98.4%) as the fully exact one. This is the cheapest performance upgrade in the whole study: no new hardware required.

Based on 22 matched H100 precision comparisons per model. The most extreme compressed format for live serving (rather than training) is still being validated for two of the three models.

Question 4

Do the chips waste time talking to each other?

When several chips work on the same job, they periodically have to "check in" with each other to stay in sync. If that check-in step takes too long, it eats into the time saved by using multiple chips in the first place.

Time spent checking in, per step

2 chips working together · milliseconds · lower is better

Getting data ready for the chip

A simple loading setting, switched off vs. on · milliseconds · lower is better

Finding The premium chip barely notices the coordination step — the budget chip notices more

On the premium chip, checking in with the other chip took well under a thousandth of a second — a rounding error next to the actual work being done. On the budget chip doing the identical job, that same check-in took 6 to 46 times longer (still a small slice of total time, but a much larger one). Separately, a simple data-loading setting called "pinned memory" cut data-preparation waiting time by over 90% — though in these tests the chip itself was always the bottleneck, not the data feed, so turning it on didn't change overall speed by much. It's still worth switching on: it's free and never hurts.

Based on 28+ communication tests and 16 data-loading tests, both platforms.

Question 5

Premium chip or budget chip?

The project compared NVIDIA's premium H100 chip against the more affordable L40S chip, using identical jobs on both, so the comparison is apples-to-apples.

How much faster was the premium chip?

Same job on both chips · right of the line = premium chip faster · left of the line = budget chip faster

Finding The premium chip's advantage depends heavily on the job

For training, the premium chip was consistently and clearly faster — about 2.4–2.7 times. But for simple, one-request-at-a-time use (generating text or classifying a sentence), the gap nearly vanished: the two chips tied on text generation, and the budget chip was actually 14% faster than the premium one for text classification in this test. If your main job is training models, the premium chip earns its price. If your main job is serving individual requests, the budget chip may be a smarter buy than its price tag suggests.

Based on 4 matched training/inference pairs across two model types, both chips.

Question 6

What's the best way to serve many people at once?

When a chip is answering requests (for example, generating text for users), it can either handle them one at a time, or group several together and answer them almost simultaneously — similar to a bus picking up many passengers on one trip instead of running an individual taxi for each person.

Each person's typical wait time

Finding Grouping requests together was one of the most effective levers we found

Serving 32 requests together got 26.7 times more total work done per second than serving them one at a time — while each individual person's typical wait time grew by only about 20%. If you're running a service with many simultaneous users, batching requests together is a very cheap way to get far more value from the same chip.

Based on 6 matched batch-size tests on the H100 chip, text-generation model.

Question 7

Does any of this actually save electricity?

Everything so far has been about speed. But chips draw real electricity while they work, and a faster chip isn't automatically a more efficient one — it might just be drawing more power to get there. This section checks whether the speed wins above also turned into using less electricity per finished piece of work, using the project's own power-meter readings taken directly off each chip during the tests (not estimates).

Finding Compact number formats save even more electricity than they save time

For the text-classification model, the most compact number format used about 17.5 times less electricity per finished piece of work than the most exact format — noticeably more than its 5.3× speed gain from earlier, because the chip also draws a bit less power per second while working in the compact format. Same free upgrade, extra payoff.

Finding More chips drew more power, but finished the job so much faster that total electricity use per job went down

Going from 1 chip to 4 roughly tripled the total power being drawn (625 → 1,961 watts, not a full 4×, since each individual chip also settled into a slightly lower power draw once shared across more of them). But because the job finished so much faster, the total electricity spent per finished job actually dropped by more than half. Adding chips wasn't just a speed win here — it was an efficiency win too.

Serving requests in groups — energy per 1,000 responses

Text-generation model, one chip · efficiency relative to serving one request at a time · higher is better

Finding Grouping requests together was the single biggest electricity saver in the whole study

The chip only drew about 14% more power when busy serving 32 requests at once compared to serving one at a time (132 → 150 watts) — but because it got through so much more work in that time, the electricity cost per individual response dropped by about 95%. If you're running a service for many people, this is the highest-leverage change measured in this entire project, for either speed or electricity use.

Power and energy figures use the project's "measured-region" telemetry — power draw sampled directly from the chip during the timed portion of each run, excluding warm-up and shutdown. Full-window estimates are excluded from these figures.

Question 8

Does all this still hold for a real, modern 7-billion-parameter chat model?

Everything above uses two small, easy-to-train models (GPT-2 Small and DistilBERT) so that many conditions could be tested quickly. This section checks whether the same patterns hold up on a much larger, more realistic model — Qwen2.5-7B-Instruct, a real instruction-tuned chat model — using a fresh batch of tests run on the premium chip (H100) on 26–27 September 2026.

Finding Compact 4-bit formats cut memory by more than half, and two of them are faster, not slower

Two 4-bit formats (AWQ and GPTQ) served requests 8–12% faster than the uncompressed BF16 control while needing well under half the memory (about 6.7 GB peak vs. 15.7 GB). A third format (NF4, bitsandbytes) used a similar amount of memory but ran nearly 3× slower, so the memory-vs-speed trade-off depends heavily on which compact format you pick — it isn't automatic. All three stayed within roughly 8–13% of BF16's answer quality (measured as perplexity on held-out text; smaller deltas are better).

Batch of 8 requests, H100, 6 trials per format. Quality deltas use a follow-up, higher-trial-count re-run (E270–E273) for tighter statistics.

Time to first word, by prompt length

Qwen2.5-7B-Instruct, BF16, H100 · real multi-thousand-word prompts · lower is better

Finding Longer prompts take proportionally longer to start responding, with no nasty surprises

Doubling the prompt length from about 4,000 to about 8,000 tokens roughly doubled the wait before the first word of the reply appeared (96ms → 200ms) — a clean, predictable relationship rather than a cliff. For a chat application, even the longest prompt tested here still starts responding in well under a quarter of a second.

Training speed by splitting method, at 7B-model scale

Qwen2.5-7B-Instruct training · higher is better

Finding The "memory-smart" splitting method's advantage gets bigger, not smaller, on a real 7B model

On the two small models earlier in this report, the memory-smart method (FSDP) was roughly on par with or modestly ahead of the alternative (DeepSpeed ZeRO-3). At 7B-model scale the gap widened substantially: FSDP was about 1.8× faster with 2 chips and about 2.1× faster with 4 chips — while also using less memory per chip in both cases. For a model this size, the choice of splitting method matters considerably more than it did for the smaller models.

3 trials per condition. These are short training runs focused on infrastructure performance (throughput, memory), not on producing a converged, high-quality model, so no accuracy/quality figures are reported for this comparison.

Finding At 7B scale, the splitting method decides whether the model comfortably fits — or barely does

The earlier memory-tuning tests in this report (batch size, gradient accumulation, activation checkpointing) were only ever run on GPT-2 Small and DistilBERT — neither is large enough to seriously test a chip's 80GB capacity. This 7B model is. With 2 chips, the memory-smart method (FSDP) used 62.1GB per chip, comfortable headroom, while the deepest-sharding alternative (DeepSpeed ZeRO-3) used 77.4GB — within about 3GB of the H100's ceiling. With 4 chips both methods have far more room (42.7GB and 50.8GB). So this project's small-model memory studies don't directly cover a model this size, but this strategy comparison stands in for that question at 7B scale: the splitting method is what keeps the model safely inside memory, not just faster.

Same runs as the finding above (E252–E255, 3 trials per condition).

Putting it together

What this means in practice

Plain, practical takeaways from everything tested so far.

Compress your numbers first. It was the single biggest, cheapest speed win in the whole study (up to 5.3×), with no measured accuracy loss.
Default to the "memory-smart" splitting method when using several chips — it matched or beat the simple full-copy method while using less memory.
Adding chips is worth it, up to 4. Expect 91–97% of the theoretical benefit if the job scales with the hardware, a bit less (73%+) if you're splitting one fixed job.
If you're serving many users, batch their requests. 26.7× more throughput for roughly 20% more individual wait — a very good trade.
Buy the premium chip for training; consider the budget chip for simple serving. The price gap is easiest to justify when you're training, hardest to justify for light, one-at-a-time inference.
Turn on the free, low-risk switches. Pinned memory loading and activation checkpointing (memory-saving pause points) each cost little and help when you're memory-constrained.
Speed and electricity use moved together in every test. Nothing measured here was a speed-for-energy trade-off — the faster option was consistently the more efficient one too, especially compact number formats and batching.

This strategy comparison (E252–E255) is the closest thing this project has to a memory-capacity study for a large model: the pipeline's dedicated "Memory optimisation" phase (micro-batch size, gradient accumulation, activation checkpointing) was run only on GPT-2 Small and DistilBERT (25 of 31 planned conditions completed), never on this 7B model.

How complete is this picture?

This summary is built from 217 completed tests out of 238 planned (91%).

Almost every planned test has run. The small remainder is a handful of specialised cases (an alternative serving engine for one model, and a couple of extra-compressed number formats) that need specific extra tooling before they can run — they don't change any of the findings above. A full technical breakdown, with every underlying number and confidence interval, lives in the project's detailed research dashboard alongside this page.
